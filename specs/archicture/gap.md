| Minimal-copy policy (`R-ARCH-7.*`) | ⚠️ | New `requirements.md` §7 consolidates the warm-path copy floor. **Met:** allow-list (R-ARCH-7.1); reference-by-handle for large payloads (R-ARCH-7.3, `DrawUniformHandle` intern); construct-in-place constant upload (R-ARCH-7.4/7.5) — VS/PS dirty cbuf bytes now build directly into the shared `MTLStorageModeShared` transient slab via `buildAndPointEntryBytes` (`src/dxmt9/dxmt9_argbuf_hybrid.cpp`), removing the per-draw stack buffer + memcpy; byte-identical, covered by `dxmt9-argbuf-hybrid-spec`/`dxmt9-argbuf-populator-spec` and the R-BACK-12.27 runtime A/B equivalence harness. **Partially met by default:** R-ARCH-7.2 + carrier part of R-ARCH-7.4 now skips the `FlatDrawStateRecord`+`shaderLayout` copy for same `{stateGeneration,stateLane}` non-front submissions in `snapshotDrawSubmissionFromCurrentState` (`src/d3d9/core_draw.cpp`). `submitDrawRunBatch` (`src/dxmt9/dxmt9_command_queue.cpp`) keeps normal compatibility grouping and accepts elided candidates through the already accepted previous draw when needed; `DXMT9_DRAWRUN_GROUP_BY_GEN_LANE=1` remains only a stricter stamp-only diagnostic mode. Counters `d3d9_snapshot_state_{materialized,elided}{,_bytes}` and `submit_draw_run_batch_discarded_state_{records,bytes}` expose the copy-class proof. The 2026-06-14 3DMark05 GT1 default scout removes the measured discarded-state class (`411,362 -> 0` discarded records), elides `412,180` state copies / `4.217GB`, and cuts `d3d9_snapshot_state_copy_cpu_ms` `261.001 -> 138.856` with a normal output frame; GPU/completion remain flat/noisy, so this is copy-policy cleanup rather than the FPS owner. The adjacent uniform-payload extension is measured and rejected for GT1: state elision fires, but `d3d9_snapshot_uniform_elided=0`, so same-stamp groups still change uniform generation. **Still needed:** deeper producer-carrier/direct-construct work if R-ARCH-7.2/R-ARCH-7.4 are to remove the surviving front/materialized state carrier copy, plus continued no-gputrace/FPS evidence before treating copy cleanup as a pacing fix. Owners: `R-ARCH-7.2`, `R-ARCH-7.4`, `R-ARCH-7.6`. |
| PE device hot/cold decomposition (`R-ARCH-1.*`, `R-ARCH-5.*`) | ✅ | **Landed 2026-08-22, eleven steps.** `src/d3d9/d3d9_pe_device.cpp` was one 16,451-line translation unit whose `D3D9DeviceImpl` class body held 453 members with every method defined in-class, so the hot/cold boundary existed only in a reader's head. Final shape: `d3d9_pe_device.cpp` 34 lines (key function + `CreateDeviceImpl`), `d3d9_pe_device_impl.hpp` 5,965 (the hot path: state, nested types, inline helpers, the CORE recorder/append path, hot COM), plus four cold TUs — `_tape.cpp` 3,676 and `_diag.cpp` 3,069 (both default-off subsystems, 65% of the internal mass), `_com_cold.cpp` 2,199 (96 virtual `Get*`/`Create*`/caps/stateblock/reset methods), `_swvp.cpp` 1,996 — and seven `.inc.hpp` regions totalling 545. **The decomposition axis was subsystem, not `Set*` vs `Get*`:** RENDER_TAPE and DIAG are default-off but hot-*reachable*, so reachability analysis marks them hot while execution never enters them. **Gate story:** steps that kept one TU were proved by object byte-identity (`825,537 B` unchanged four times, plus a textual expansion reproducing the original line-for-line); once code left the TU that became impossible, so it was replaced by a normalised instruction-stream diff of the hot methods against the previous step (30/30 at each of steps 7-10, with the single reduction at step 9 explained rather than waved through). A declaration-set diff mutation-proven to catch a dropped default argument on a virtual override carried the silent-behaviour-change risk, and the `ProcessVertices` text audit was retargeted and re-mutation-tested (5/5) rather than weakened. Behavioural evidence: host suite 731/731 throughout (it structurally cannot see this TU — 0 targets in `build`, 1 in `build-win32-x64-builtin`), and for the cold-COM step two full conformance runs per build, discriminating by reproducibility rather than count, with no case failing in both step-10 runs except the known `visual_process_vertices_xyzhw_policy` fixture defect. **Honest negative:** clean `build-win32-x64-builtin` got *worse* — 26.90 s → 28.98 s wall (+7.7%), 130.6 → 140.0 s user CPU, measured ABBA to control the thermal drift that a naive series showed. One 4.02 s TU became five totalling 8.69 s; the critical path halved (4.02 → 2.08 s) but the machine had spare cores, so the doubled parse work surfaced as wall time. The split bought incremental-edit locality, reviewability, and a structural hot/cold boundary — not build throughput. `d3d9.dll` +1.03% (x64) / +1.87% (x86). Two language constraints discovered by measurement are recorded in `agents/rules/codebase_conventions.rules.md` §"Moving Code Between Translation Units". |
| PE-side type-level safety (`R-ARCH-1.*` adjacent) | ⚠️ | **Measured 2026-08-22.** Across `src/d3d9/d3d9_pe_*` (~32k lines) versus `src/dxmt9/*`: `enum class` 20 vs 135, `constexpr bool` pure predicates **4 vs 151**, `static_assert` 30 vs 120, TLA+ binding comments ~17 vs 104, `std::variant` 0 in both (PE's single occurrence is a comment recording why one was rejected). The shared-pure-predicate discipline that binds a TLA+ action to production code and to a native spec (R-BACK-43.6 shape: `pendingInitializerReferenceSafe`, `drawableTokenMayFulfill`, `canReclaimRecord`) is therefore almost entirely a unix-side achievement with no PE foothold. **Root cause, and the reason this is architectural rather than stylistic:** `d3d9_pe_device.cpp` and its siblings are in `dxmt9_pe_core_srcs`, compiled only `if host_machine.system() == 'windows'`, so **the host suite cannot compile or observe them at all** — verified: 0 targets in `build`, 1 in `build-win32-x64-builtin`. PE's safety story is consequently differential golden testing (`dxmt9-pe-producer-differential-spec`), value-level mirrors of pure validators, and validation at the unix import boundary — never type-level invariants, because there is no host lane in which to assert them. **Closed so far:** typed slot keys for the state shadow (`98fceb13`) give the six index spaces — render-state, texture-stage, TSS type, sampler, sampler-state type, transform — distinct `enum class ... : std::uint32_t` keys, making cross-space indexing a compile error; zero runtime cost proven by `static_assert` on size/align/trivial-copyability, storage `sizeof` pinned to pre-change literals, and machine-code comparison (`producer.o` `__text` byte-identical, `process_vertices.o` `.text` size-identical). **Correction 2026-08-22:** an earlier draft of this row claimed the PE recorder's thread-affinity contract was "an ad-hoc assert plus an env override" and listed adopting `ThreadOwnershipToken` as outstanding work. That was wrong and was never checked before being written — the recorder already holds a `dxmt9::core::ThreadOwnershipToken recorderOwnership_` and asserts through `DXMT_ASSERT_OWNED_BY_OR_LOCKED(recorderOwnership_, recorderLockRequired_)`, and its own comment records that this site is the reference shape the shared helper was *extracted from*. PE led that pattern rather than lagging it. The error came from extrapolating a specific mechanism claim out of aggregate grep counts, which the metric caveat in this row explicitly warns against. **Migration completed 2026-08-23** (`04a898f4`, `ae1479a9`): every keyed table access across the five `D3D9DeviceImpl` TUs and the producer now goes through the typed views — zero untyped `get`/`set`/`contains`/`erase` remain — and the raw `PeHotStateShadow::renderStateEquals` convenience, left callerless by the migration, was deleted so no untyped door stays open. Codegen was verified rather than assumed: per-symbol instruction comparison of the hot object shows **all 24 hot methods instruction-identical**, and of 302 symbols only four differ — `InvalidateStateBlockShadowForChild` and its thunk at an unchanged 80 instructions, an `appendSingleCategoryApplyState` instantiation at an unchanged 118, and `drainOversizedPendingStateAsApplyStateRecords` at +3 (a bounded overflow-drain path, not per-draw). The typed views forward directly (`clear()` is `table_.clear()`), so those four are the compiler choosing a different but equivalent store sequence, not added work. **Still needed:** (a) decide whether making `dxmt9_pe_core_srcs` host-buildable is worth it, since that, not more types, is what would give PE a unit-level behavioural gate. |
