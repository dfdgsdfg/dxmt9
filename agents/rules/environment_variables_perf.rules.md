# dxmt9 Environment Variables — Perf counters

Part of the [`environment_variables.rules.md`](environment_variables.rules.md)
index (counter system, per-frame snapshot, and 3DMark05 GT1 perf-probe knobs).
A flag is "set" when its value is a non-empty string that is not `0`, unless
documented otherwise. See the index for global notes, and
[`metal_debugging.rules.md`](metal_debugging.rules.md) §9 for the 3DMark05 GT1
perf-probe toolkit.

| `DXMT9_SCHEDULING_PROGRESS_WATCHDOG_MS` | Diagnostic-only scheduling liveness threshold in milliseconds. Requires `DXMT_PERF_COUNTERS=1`; unset or `0` performs no env-dependent watchdog work, clock reads, atomic tracking, or sampler-thread creation. When enabled, a CommandQueue-owned fixed 256-slot ledger serializes each generation identity across writers and sampling, then emits bounded, threshold-rate-limited warnings for stalled admission, first lease, publication, encode/open-session, submit, GPU settlement, completion expansion, and Present release, including explicit skip, stop/loss, capture, and tracking-overflow attribution. Suspend attribution is intentionally absent until the Metal 4 lane exposes a real tested disposition. The watchdog never changes scheduling, wakes, recovery, or fatal behavior | unset |
> **Do not price encode-thread instrumentation against frame wall.** GT2's
> encode thread carries `~17 ms/present` of slack, so CPU added or removed there
> is absorbed by waiting and never reaches the frame. A no-op-`PerfScope` A/B
> measured `0.12 ms/present` (`0.3%`) that way and concluded the encode timers
> were nearly free; against the **encode stage wall** — the event-timestamp
> counter `completion_no_enqueue_stage_encode_dequeue_to_command_buffer_commit_ms`,
> which survives a no-op build — the same two runs price the `PerfScope` family
> at **`4.64 ms/present`, `11.5%` of the frame**
> (`state-churn-encode-append-decomposition.13`). A clock read is `~43 ns` here
> against `~180 ns` on the PE side through Wine's `QPC`: four times cheaper, not
> free. So the heavy `DXMT9_PERF_*_SPLIT` gating below **is** about cost, and
> new encode-side scopes need it — `DXMT9_PERF_ENCODE_DRAW_PHASE_SPLIT` was
> added for exactly that reason after its timer shipped ungated on the wrong
> number.

| `DXMT9_PERF_DRAIN_FENCE_SITES` | Attributes the commit-replay offload's drain fence (`R-BACK-2.51(d)`) to the bridge entry point that blocked. 84 `dxmt9c_*` shims call `drainDeferredReplay`; the aggregate `offload_drain_fence_wait_ms` counter says the producer blocks but not where. Global site rows remain recorded **only when a drain actually blocks** (`depth()==0` returns early), while the resource-scoped buffer path also emits a cumulative `fence_mode` histogram for global/scoped waits, already-clear scoped calls, calls that bypassed unrelated queued work, valid dynamic-DISCARD/NOOVERWRITE bypasses, and terminal rejection. The sink buckets a blocked call site's string-literal pointer rather than its content. Emits cumulative `[dxmt9-drain-site]` lines every 60 presents at Info level (`--dxmt-log-level info`) — **not** at device teardown, because 3DMark05 never releases the device and a destructor-emitted report is silently lost. Also classifies a blocked `buffer_lock` by flags and pool at the moment it blocks, emitted as a `blocked_lock_class` line beside the site rows — read all lines from the **same** emission, since they are cumulative. GT2 predecessor: `dxmt9c_buffer_lock` was `99.8%` of the global fence (`present-pacing-drain-fence-attribution.206`) and the blocked subset was `54-57%` MANAGED, skewed `7x` toward DISCARD versus the all-locks mix (`.207`) | `0` |
| `DXMT9_PERF_QUEUE_MUTEX_SPLIT` | Attributes `CommandQueue::mutex_` contention (`src/dxmt9/dxmt9_command_queue.cpp`) to the call site that acquired it. GT2 showed the producer's commit-time mark phase alone spends `38.7 us/call` (`0.617 ms/present`) just ACQUIRING the mutex (`commit_chunk_phase_mark_lock_cpu_ms`); the same mutex is shared by the game thread (mark/capture, ~16 calls/present), the replay offload worker (`submit*`, hundreds of calls/present), the encode thread, and GPU completion handlers, so an aggregate number cannot say which caller to fix. Follows the `DXMT9_PERF_DRAIN_FENCE_SITES` sink pattern: a small RAII guard (`QueueMutexProbeScope`) at every acquisition site buckets on the `site` string-literal pointer into a fixed 64-slot table (overflow folds into one row), recording per-site acquire count, total acquire-wait, and — where meaningful — total/max hold time. Covers all 41 acquisitions of the `mutex_` member plus one more (`submit_draw_run_batch_impl`, which locks the same mutex through a `std::mutex&` reference parameter and is the hot per-draw-run-batch path called by the replay offload worker). Many sites hand their `std::unique_lock` to a `condition_variable::wait()` or to a `QueueLifecycleController` helper (`ensureWritingSlotUnlocked`, `maybeCommitDrawPayloadArenaUnlocked`, `maybeCommitDrawChunkUnlocked`, and `queueLifecycle_.*`, all in a different file) that may unlock/relock it an unbounded number of times; those sites record only the initial acquire-wait and skip hold accounting (tagged `-cv` for a direct condition-variable wait, `-relock` implicit in the site's own doc comment otherwise) rather than report a number with no single meaning. Emits cumulative `[dxmt9-queue-mutex]` lines every 60 presents at Info level from `CommandQueue::submitPresent`, mirroring the drain-site sink's periodic-not-teardown reasoning (3DMark05 never releases the device). Diagnostic only — not a perf sample; the guard adds a `steady_clock::now()` pair per acquisition when enabled | `0` |
| `DXMT9_PERF_COMMIT_CHUNK_PHASE_SPLIT` | Heavy opt-in phase split of the **synchronous half** of `dxmt9c_device_commit_chunk`, the unix-side body of a PE chunk flush. Splits the wall that `offload_commit_app_cpu_ms` already measures into `commit_chunk_phase_{prepare,import,mark,enqueue}_cpu_ms` plus `commit_chunk_phase_present_wait_ms`, with `commit_chunk_phase_calls` as the denominator. `present_wait` is broken out on purpose: the parent timer spans `waitPresentOrdinalBoundary`, so a blocking wait is inside the number and leaving it lumped overstates the CPU terms. Motivated by `state-churn-encode-append-decomposition.05`, which found `69-72%` of that half is fixed per call (`~22-23 us`) and could not say which phase owns it. Adds five clock pairs to a call that runs tens of times per present, so pair every ON run with an OFF control and read the parent counter to size the perturbation before trusting the split. The mark phase (`commit_chunk_phase_mark_cpu_ms`, measured `0.888 ms/present` = `62%` of the sync half on GT2, `56.5 us/call`) is further split into its three PE-side owners inside `persistResolvedResourcesAndCaptureBindings` (`src/d3d9/device_c_chunk_replay.cpp`): `commit_chunk_phase_mark_dedup_cpu_ms` (the resolved-handle dedup loop — a `std::find` over `raw.ledgerTargets` per buffer handle plus a `std::any_of` over `scratch.coreEntries` per handle, both O(n^2)), `commit_chunk_phase_mark_core_cpu_ms` (the single call into the core `upperDevice`, which on the default lane subsumes `commit_chunk_phase_mark_lock_cpu_ms`'s queue-mutex acquire wait), and `commit_chunk_phase_mark_sort_cpu_ms` (the `raw.bufferSnapshots` sort), plus per-call `commit_chunk_phase_mark_handles` / `commit_chunk_phase_mark_buffers` counts so dedup/core cost can be divided into a per-handle/per-buffer figure. `commit_chunk_phase_mark_lock_cpu_ms` itself used to be wired only into the legacy `CommandQueue::markChunkResources` path and always read `0` on the default (non-CpuReadyTape) lane, because the production caller is `markChunkResourcesAndCaptureBufferBindings` (`src/dxmt9/dxmt9_command_queue.cpp`), which never timed its mutex acquire; both functions now share one `markChunkPhaseSplitEnabled()` env-gate helper and both time the acquire | `0` |
| `DXMT9_PERF_ENCODE_DRAW_PHASE_SPLIT` | Sequential partition of `encodeDraw` into eight phases (`encode_draw_phase_*_cpu_ms`) that sum to `encode_draw_cpu_ms` by construction, so the branches between the `PerfScope` children — a third of the reading, which they leave uncounted — have somewhere to land. Nine clock reads per draw, `0.645 ms/present` (`1.6%` of the GT2 frame), so opt-in only. Note the `remainder` phase is what measures indexed-setup and draw-issue on the common path, because `encodeDraw` returns from inside a nested block before the last mark. The same flag also splits the eleven multi-call-site children (`encode_draw_{stream_bind,fvf_decode,uniform_build}_*`), without which the per-phase named/unnamed split cannot be computed at all — those sites straddle phases and two published hand-mappings of them were wrong (`.15`). Each costs one atomic add and no extra clock read | `0` |

## Retired perf diagnostics

`DXMT9_PERF_DRAW_PACKET_ACTUAL_CHANGE` is **not honored by the current HEAD**.
It compared a draw packet's declared state bits against the unix-side
`DeviceState` and bucketed actual-changing versus redundant deltas. The whole
premise was the fat `D9CDrawPrimitivePacket`, which the PE legacy-record removal
deleted: there is no packet delta to compare any more, only sparse canonical
sections that carry exactly what the producer decided to emit. Removed together with its
`drawPacketActualChangeMask` implementation, every `draw_packet_*` counter it
fed, and the wrapper's `--probe-draw-packet-actual-change` flag;
`summarize_3dmark05_perf.py` keeps its tolerant rows so historical `result.json`
files still parse.

Deleting the writer left the counters behind at first -- eighteen `draw_packet_*`
fields with live `kCounterTable` rows and nothing writing them, reporting `0` on
every `[dxmt9-perf]` line. Neither existing audit could see it: the table audit
passed because the rows were present, and the callsite audit had nothing to check
because the `count*()` declaration had gone with the function. A sweep for the
same shape found **165** such fields in total, most of them orphaned when the
legacy replay path was deleted (`commitChunkReplay*Record*`,
`commitChunkDrawDelta*`, and the retired command-chunk fields). All are gone, and
`scripts/check/audit_perf_counter_table.py` now checks the second direction --
a field with a table row that no writer anywhere names -- so the shape cannot
come back. A counter stuck at zero is worse than a missing one: it reads as
*measured and negligible* rather than *not measured*. Do not schedule new
runs with this env unless an equivalent sparse-section diagnostic is
intentionally written, and update this file in the same change.
