# The offline prefix saving does not establish a live saving

The fixed H538 population completes in order **A0, A1, A2, B1, B2, A3**, without
retries, exclusions or extra game runs. Both opposite-order comparisons fail
to establish Replay CPU reduction beyond the A0/A1 uncertainty envelope.
Keep the candidate private; do not promote it or convert H537's offline
3.379 ms/captured-interval saving into a live ms/frame budget.

All games exit zero after seven qualified spatial endpoints. Post-tail images
are visually coherent; these screenshots are not whole-run pixel equivalence.
H538's earlier same-input original pixel/source/query checks remain the separate
correctness evidence. The current results do not establish the largest
**default** dxmt9 single-thread owner or a positive removable CPU amount.

## Method and administrative deviation

Use the unchanged H538 private matched images: common boundary-only PE and
sparse worker CPU reporters, A full-prefix preparation versus B suffix
preparation. Sikarugir CX24.0.7, Day/high, 1280x720, max-threads 2,
snd_targets 16, command limit 0, production-counter occlusion. Product
perf/frame/supply/capture observers stay OFF. These controlled game settings
are not a claim about untuned application defaults. No build or test overlaps
the live runs. Computer-use is limited to startup window restoration and
post-window screenshots; A0 also has a pre-window read-only screen inspection.

Every frozen runner encounters the same **post-completion** restoration guard:
the Wine server remains briefly after its clients exit. The server then exits
without a kill or restart. Before inspecting any CPU result, a separate
administrative amendment retains the failed receipts and permits authenticated
deferred restoration. It does not change the sample population or numerical
screen. The original `compare.py` rejects `restore_blocked`; therefore these
results are explicitly an **administratively amended comparison**, not a pass
of the original frozen qualification.

`recover_exit.py` proves no Wine process remains, verifies the original backups
and staged identities, preserves currently installed files, restores all 14
original files, and moves four temporary service files into retained evidence.
Each receipt retains `restore_blocked` and appends a recovery-qualified cleanup.
`receipt-before-recovery.json` preserves its exact previous bytes. Catalogue
reports only `missing_capture` under the predeclared delayed-capture policy;
game exit zero is not relabeled a catalogue pass.

`analyze_amended.py` first authenticates each recovery, then uses the frozen
CPU parser with only that post-completion rejection handled separately and
a different output filename. Independent decoding of binary rows recomputes
all **108 thread intervals** (6 runs × 6 spans × 3 threads). Original/current
receipt equivalence, execution order, input hashes, no dropped/faulted rows,
thread identity, restoration, frame counts and numerical bounds all pass.
Final readback checks all 48 comparison hashes, all six recovery chains,
restored live files and 18 independently recalculated numerical screens.

## Finite economy screen

Positive delta means A costs more than B. Require both opposite-order lower
bounds to exceed the entire A0/A1 endpoint-difference envelope. The predeclared
primary metric is Replay; other scopes are secondary.

| Scope | A/A envelope | A2−B1 | A3−B2 | Both pass |
|---|---:|---:|---:|---|
| Replay | 0.452 | −1.002 to −0.374 | −0.279 to +0.505 | No |
| Encode | 0.387 | −1.200 to −0.775 | −0.114 to +0.543 | No |
| Primary | 2.084 | −0.196 to +1.551 | +0.102 to +1.848 | No |

Units are ms/frame. None of the five Replay component screens passes either.
Do not select the one favorable Encode component or pool opposite-order runs
to rescue the primary result. A2→B1 shows higher candidate CPU; the reverse
comparison overlaps zero. This is not proof of an intrinsic candidate
regression, zero true saving, or a particular thermal/scheduling cause.

Host censuses outside the target window contain varying Spotlight, Biome,
Siri, WindowServer and Orca activity. They do not price within-window
interference; no host estimate is subtracted. Observed tail cadence spans
approximately 16.27–18.95 FPS, but this is not a clean FPS baseline, a README
update or an attributed FPS improvement.

## What the current observations narrow

Encode CPU bounds exceed Replay in all six complete diagnostic intervals.
That makes Encode a stronger current dedicated-worker candidate, **not yet a
canonical/global maximum**. The mixed Primary totals cannot be compared as
exclusive dxmt9 cost. H534's older all-root upper bounds are useful history,
not a new root attribution for these boundary-only runs.

`clock_windows.py` independently totals the recorded `proc_pidinfo` wall
brackets in the same spatial interval: Replay 0.0146–0.0161 ms/frame and
Encode 0.0303–0.0390 ms/frame. These clock-call windows are much smaller than
the observed worker totals. They exclude emit reservation/row initialization,
metadata, request checks, shared-cache effects and changed scheduling. They
must not be subtracted as the complete observer cost or used to certify
common-observer-to-canonical transfer.

Decision: stop treating prefix-prepare as a demonstrated live removal. The
next attribution gate is residual-observer/canonical qualification and actual
Encode work ownership, not another identical prefix FPS retry. If the prefix
mechanism itself is revisited, first establish its live eligible/accepted work
population in an unpriced diagnostic: the 199-prepare witness is from the
frozen offline input, not a live-tail census. No largest-default-owner or
positive canonical removal budget is closed here.
